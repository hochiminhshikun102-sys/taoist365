# Maintenance Ordinaryness

This file keeps maintenance ordinary.

It should stay short.

## Purpose

Most maintenance is just maintenance.

Do not turn every repair into a statement about the whole project.

## Ordinary Repairs

Many changes should be described plainly:

- fix broken text;
- update a link;
- remove confusing wording;
- repair mobile spacing;
- check a guardrail;
- update a deployment note;
- replace an object image;
- fix an access issue.

These do not need larger framing.

## Commit Language

Commit messages should become simpler over time.

Prefer:

- `fix object image path`;
- `thin homepage copy`;
- `update deployment note`;
- `repair admin wording`;
- `add observation log`;
- `fix ai-readable json`.

Avoid:

- manifesto sentences;
- philosophical framing;
- dramatic continuity language;
- identity claims;
- poetic maintenance wording.

A commit should help someone understand the change, not feel the project.

## Observation Notes

Observation notes should read like maintenance residue.

Prefer:

- date;
- surface;
- device;
- issue;
- repair needed;
- leave alone.

Avoid:

- essay structure;
- new concepts;
- emotional description;
- grand framing;
- repeating the same identity terms.

## Repair Is Not An Event

A repair should usually happen quietly.

Do not frame ordinary repair as:

- a milestone;
- a new era;
- proof of importance;
- continuation of a worldview;
- a special act.

If a fix is small, describe it small.

## Documentation Should Thin

Late-stage documentation should become:

- thinner;
- calmer;
- lower-energy;
- less conceptual;
- less identity-driven;
- easier to scan.

It should not become thicker just because the project has more history.

## Ordinary Is Not A Style

Do not perform ordinary.

Ordinary maintenance means the work does not keep pointing at itself.

It is not:

- an aesthetic;
- a brand tone;
- a writing posture;
- a new identity;
- another way to sound special.

## Maintenance Performance Observation

Watch for maintenance becoming performance.

Risk signs:

- small fixes are described like large moments;
- notes sound like worldview continuation;
- commit messages become poetic;
- restraint is explained repeatedly;
- documents emphasize project specialness;
- ordinary decisions receive ceremonial language.

When this appears, shorten the note.

## Rule

The best maintenance record is usually the plain one.
