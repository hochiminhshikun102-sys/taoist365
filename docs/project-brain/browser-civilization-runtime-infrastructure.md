# Long-Term Browser Civilization Runtime Infrastructure

This file governs runtime durability for Reverent Inquiry. It does not authorize new runtime layers, new pages, organism proliferation, feature showcases, or atmosphere expansion.

## Runtime Posture

Runtime should now behave like infrastructure: durable, transferable, maintainable, low-pressure, browser-native, and quiet. The goal is not a larger concept collection. The goal is fewer reasons for the civilization to deform.

Executable check:
- `npm run guardrail:runtime`

The runtime guardrail freezes the current runtime budget, active `useWorldRuntime()` field set, required runtime files, required data directories, and runtime naming boundaries.

## Runtime Orchestration

`buildRuntime()` in `src/lib/use-world-runtime.ts` is the active orchestration chain. Its resolver order is frozen by `npm run guardrail:runtime`.

Do not add a top-level resolver to the chain unless an existing resolver cannot absorb the responsibility. Prefer composing under existing fields before changing orchestration.

## Runtime Thinning Strategy

Do not add a runtime because a phrase feels new. Prefer one of these actions:
- fold the phrase into an existing runtime
- retire it into documentation
- keep it as archive context
- express it through existing Browser Air tokens
- leave it unimplemented

Add a runtime only when it has a distinct persistence job that cannot be carried by an existing runtime.

Current frozen budgets:
- `src/runtime`: 122 TypeScript files
- `src/data`: 113 top-level data directories
- `WorldRuntime`: 26 top-level fields

Any increase should be treated as runtime inflation unless paired with a retirement or consolidation.

## Runtime Hierarchy

Runtime roles:
- active runtime: directly read by UI or page shells
- infrastructure runtime: supports thinning, persistence, governance, or static continuity
- continuity runtime: keeps browser return, object passage, mail, and ordinary time coherent
- browser residue runtime: carries long-open tab, hostname, history, and low-refresh behavior
- archive runtime: historical or superseded concept, not a reason to add UI behavior

`useWorldRuntime()` is the active top-level boundary. New top-level fields should be avoided; compose under existing fields instead.

## Windkeep Runtime Infrastructure

Windkeep should remain object continuity infrastructure: keeper traces, shelf persistence, Quiet Receiving, practical object passage, and ordinary stewardship.

It must not become object experience layering, marketplace backend, inventory system, ownership pressure, auction energy, collectible logic, or checkout behavior.

## Driftbox Runtime Infrastructure

Driftbox should remain low-frequency browser current: sparse continuity, unresolved drift, quiet receiving, object movement, and non-assistant intelligence.

It must not become an AI assistant system, chatbot, reply loop, interaction surface, productivity helper, or expectation engine.

## The Courier Runtime Infrastructure

The Courier should remain quiet organism runtime governance: lightly irregular, low-attention, browser-native micro-life.

Organisms must not become feature modules, dashboard panels, utility systems, gamified actors, or attention competitors.

## Pocket Browser Runtime Infrastructure

Pocket Browser should preserve phone-browser air: low-density, ordinary scrolling, stable persistence, and no app shell.

It must not add install pressure, mobile product framing, retention hooks, feed structures, assistant UI, or app-like density.

## Browser Persistence Runtime

Browser persistence should feel like a quiet place left open for a long time: stable hostname, favicon continuity, low-refresh recurrence, browser softness, and ordinary memory.

No visual nostalgia is required. Persistence is mechanical, quiet, and compatible with leaving.

## Reality Compatibility

Runtime must coexist beside ordinary life. Avoid emotional stickiness, psychological immersion, assistant gravity, refuge orientation, sanctuary formation, therapeutic behavior, and dependency patterns.

The strongest runtime is often the one that does less, updates less, and lets the browser carry memory.
